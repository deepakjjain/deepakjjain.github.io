Step Functions Is Cheaper Than Retry Logic

When your nightly Fargate job needs retries, execution history, and failure alerts — don't build that into the application. EventBridge + Step Functions gives it all for essentially nothing.

Related project: Enterprise HR Chatbot on AWS Bedrock

Our nightly knowledge-base indexer had a silent failure problem. It ran as a Fargate task triggered by EventBridge, syncing SharePoint documents into AWS Bedrock. When Bedrock throttled or SharePoint authentication timed out, the job exited non-zero. No retry. No history. No alert. The knowledge base just quietly fell behind.

The fix was not in the application code.

The Wrong Instinct

When a scheduled job fails, the instinct is to add retry logic to the application. Wrap the API call in a try/except. Add exponential back-off. Log failures somewhere.

This works. But it means your retry logic lives inside the container, invisible from the outside. You cannot see how many retries occurred, when they happened, or why they failed — not without digging through CloudWatch logs and reconstructing a timeline yourself.

There is a better place for this logic.

EventBridge → Step Functions → ECS

Instead of targeting ECS directly from EventBridge, put a Step Functions state machine in the middle:

{
  "StartAt": "RunIndexerTask",
  "States": {
    "RunIndexerTask": {
      "Type": "Task",
      "Resource": "arn:aws:states:::ecs:runTask.sync",
      "Parameters": {
        "Cluster": "${cluster_arn}",
        "TaskDefinition": "${task_definition_arn}",
        "LaunchType": "FARGATE",
        "NetworkConfiguration": { "..." }
      },
      "Retry": [{
        "ErrorEquals": ["States.ALL"],
        "IntervalSeconds": 60,
        "MaxAttempts": 5,
        "BackoffRate": 1.0
      }],
      "End": true
    }
  }
}

EventBridge fires the cron. Step Functions runs the ECS task synchronously — ecs:runTask.sync means it waits for the task to complete before proceeding. If the task fails, Step Functions retries up to five times at 60-second intervals, automatically, before returning a failed execution.

The Fargate container does not know any of this is happening. It attempts the job and exits with 0 or non-zero. Step Functions handles the rest.

What You Get for Free

Execution history. Every run appears in the Step Functions console with start time, end time, status, and retry count. You can expand any execution and see the exact sequence of state transitions.

CloudWatch log integration. State transitions — task started, task failed, retry attempt 3 — are log events. Query them with CloudWatch Insights. Build a dashboard. Set up anomaly detection on execution duration.

Alerting without code. Create a CloudWatch alarm on the ExecutionsFailed metric for your state machine. Route it to SNS. Your on-call engineer gets paged when the job fails after all retries. No Lambda notifier. No custom alerting code.

The Terraform

resource "aws_sfn_state_machine" "indexer" {
  name     = "${var.name_prefix}-indexer-sm"
  role_arn = aws_iam_role.sfn.arn
  definition = templatefile("${path.module}/statemachine.json", {
    cluster_arn         = aws_ecs_cluster.main.arn
    task_definition_arn = aws_ecs_task_definition.indexer.arn
  })
  tags = local.common_tags
}

resource "aws_cloudwatch_event_rule" "nightly" {
  name                = "${var.name_prefix}-nightly"
  schedule_expression = "cron(0 0 * * ? *)"
  tags                = local.common_tags
}

resource "aws_cloudwatch_event_target" "sfn" {
  rule     = aws_cloudwatch_event_rule.nightly.name
  arn      = aws_sfn_state_machine.indexer.arn
  role_arn = aws_iam_role.events.arn
}

Three resources. EventBridge fires the cron, targets Step Functions, Step Functions runs ECS and handles retries.

What It Costs

Step Functions charges per state transition. A single-state machine produces two transitions per execution — one to enter the state, one to exit. At $0.000025 per transition, a nightly run costs $0.018 per year.

Building the equivalent retry logic, execution logging, and failure alerting into the application is hours of engineering work and an ongoing maintenance surface. The maths is not close.

The Takeaway

Scheduled batch jobs that need retries and visibility are not an application problem. They are an orchestration problem. Step Functions solves it at the infrastructure layer, for essentially nothing, and leaves the application code doing exactly one thing.

If your nightly job is running bare on EventBridge → ECS, add the Step Functions wrapper. You will have it done before lunch.
