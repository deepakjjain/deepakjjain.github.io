FinOps: Start With Visibility, Not Cuts

Before optimising AWS spend, you need to know where the money is going. The tagging and reporting work is harder than the actual cost cuts — and more important.

Related project: AWS Cloud Cost Optimisation

The instinct when AWS costs are high is to start cutting. Turn off unused instances. Delete old snapshots. Buy some Reserved Instances.

That is the wrong order.

We reduced AWS spend by $500K+. The cuts were the easy part. The hard part was building the visibility layer that made the cuts safe and targeted.

The Problem With Cutting Blind

When you don’t know which team owns which resources, you make two kinds of mistakes:

  1. You cut the wrong things and break production.
  2. You cut the obvious things and miss the real waste.

Both happened before we changed approach. A dev database got terminated by someone trying to save money. Turns out it was used by a QA team running nightly regression jobs. The job failures were silent. The team found out two weeks later.

The lesson: you cannot optimise infrastructure you don’t understand.

Build the Visibility Layer First

Step 1: Cost and Usage Reports. Enable CUR in AWS and deliver it to an S3 bucket. This is the raw data — line-item charges for every resource, every hour. Without CUR, you are working from the billing dashboard summary, which hides too much.

Step 2: Athena for queries. CUR files are large Parquet files. Athena lets you query them with SQL without loading them into a database. Write queries for the things you actually want to know: which account spent what, which service drove the spike last week, which untagged resources are costing you money.

Step 3: Grafana for visibility. Connect Athena to Grafana and build a cost dashboard. One panel per account. One panel for top services. One panel for untagged resource spend. Refresh daily.

The goal is not a beautiful dashboard. The goal is to be able to answer “who owns this?” and “what changed this month?” in under two minutes.

The Tagging Problem

Without tagging, CUR tells you that your account spent $40K on EC2 this month. It does not tell you which team’s services those are.

We defined a mandatory tag taxonomy: team, environment, service, cost-centre. Then we enforced it in Terraform:

variable "required_tags" {
  description = "Tags required on all resources"
  type = object({
    team         = string
    environment  = string
    service      = string
    cost_centre  = string
  })
}

Any Terraform module that creates an EC2 instance, RDS database, or S3 bucket must receive these tags. We added a CI check that runs terraform plan and fails if any planned resource is missing required tags.

Compliance before enforcement: ~30%. After three months of CI enforcement on new resources and a tagging sprint for existing ones: 95%.

At 95% tagging, the cost dashboard becomes genuinely useful. You can do team-level showback. You can hold a cost review and point to specific numbers.

Then You Can Optimise

Once you can see the data clearly, the optimisation work is mostly mechanical:

Right-sizing. Pull 30-day p95 CPU and memory from CloudWatch for every EC2 and RDS instance. Any instance running below 20% p95 CPU is a candidate. Present the data to the service owner, agree on the target size, do the resize. Repeat.

Reserved Instances. Look at your baseline compute — the capacity that runs 24/7 regardless of load. That is your RI target. Buy 1-year RIs for that baseline. Do not buy 3-year unless you are very confident in stability.

Dev environment hygiene. Tag non-production resources with environment = dev. Write a Lambda that stops tagged EC2 and RDS instances at 8pm and restarts them at 7am. This is free money. Dev environments do not need to run at 3am.

What We Learned

Visibility is not a prerequisite to optimisation — it is the optimisation. Every cost cut we made traced back to a specific signal in the dashboard. None of it was guesswork.

The tagging enforcement work took three months and was genuinely tedious. But it is what made everything else possible. If you are starting a FinOps programme, tag first, cut second.
