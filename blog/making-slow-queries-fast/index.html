Going from 90-Second Queries to Sub-Second: What Actually Worked

How we made a 50M-row reporting database feel instant — materialized views, cache strategy, and the decisions that didn't pan out the way we expected.

Related project: Analytics Dashboard

Reports were taking 45–90 seconds against a 50M-row events table. Sales and ops teams had stopped trusting the dashboards. By the time a report loaded, someone had already pulled the numbers from a spreadsheet.

This is what we tried, what worked, and what did not.

Wrong First Move: Index Everything

Slow query? Add indexes. We added several. A 90-second query became 40 seconds. Still unusable.

The problem was structural. The common queries were aggregations over large time ranges: total events by day, breakdown by user segment, cohort retention. Indexes do not help here — the database has to touch a lot of rows regardless.

Indexes help selective queries. They do not help aggregation queries.

What Actually Worked: Materialized Views

Past events do not change. The query for “events per day in March” will return the same answer no matter when you run it. There is no reason to recompute it from raw data on every request.

Materialized views pre-compute the aggregation and store the result:

CREATE MATERIALIZED VIEW daily_event_counts AS
SELECT
  date_trunc('day', created_at) AS day,
  event_type,
  user_segment,
  COUNT(*) AS event_count
FROM events
GROUP BY 1, 2, 3;

CREATE INDEX ON daily_event_counts (day, event_type);

The same query that was scanning 50M rows now hits a view with a few thousand rows. Query time: 45–90 seconds → under 200ms.

The catch: the view is stale until refreshed. We ran REFRESH MATERIALIZED VIEW CONCURRENTLY on an hourly schedule. CONCURRENTLY lets reads continue against the old data during refresh — no locked window.

Caching on Top of the Fast Query

Even 200ms adds up when multiple users hit the dashboard at once. We added Redis caching with a 10-minute TTL, keyed by a hash of user ID and query parameters.

Two things easy to get wrong:

Include the user ID in every cache key. Even if the query is not user-specific. Skip this and you risk serving one user’s data to another.

Show a “data as of” timestamp. With hourly view refreshes and a 10-minute cache TTL, data can be up to 70 minutes old. Make it visible in the UI so nobody is confused about freshness.

Async Exports for the Cases That Cannot Be Fast

Not all reports fit into pre-aggregated views. Custom date ranges and complex filters cannot be covered without an explosion of view permutations.

For those, we stopped trying to make them fast. Heavy exports run as background tasks. The user gets a “processing” state immediately. When the task finishes, the result is ready to download.

This removed the timeout problem entirely. Fewer complaints than the old 90-second wait — a spinner with a clear progress state feels better than a frozen loading bar with no sign of life.

What Did Not Work: Caching the Slow Query

Before adding materialized views, we cached slow query results directly in Redis with a 1-hour TTL. The first request of the day was still slow — cache expired, someone had to eat the 60-second query to warm it.

Caching a slow query does not make it fast. It makes it slow less often. Fix the query first, then cache the fast version to handle load.

The Boring Fix Had the Biggest Impact

The events table had a metadata column with JSON blobs. Several reports filtered on values inside those blobs. JSON filtering in PostgreSQL is possible — it is just slow.

Extracting two frequently-filtered fields into proper columns and indexing them removed several of the worst queries. No architecture changes. No new services. Just schema cleanup.

Profile before you architect. We spent time designing a caching strategy before we understood the query patterns. The hardest-looking problems turned out to be simple fixes once we actually looked.
