What Three Years of Managing Monitors as Code Actually Taught Me

We moved 400 synthetic monitors from click-ops to Terraform. Here is what worked, what didn't, and the one change that made non-engineers start submitting PRs.

Related project: Observability-as-Code Platform

We had 400 synthetic monitors in New Relic. Every one created by clicking through a UI. No version history. No peer review. One misconfigured alert and you had no idea what changed or who did it.

We moved everything to Terraform and Git. Here is what three years of running it actually taught us.

The Wrong Abstraction Kills Adoption

The original design: engineers write HCL to define monitors. Version-controlled, peer-reviewed, deterministic. Correct.

Nobody used it.

Not because Terraform is hard. Because the people who knew what needed monitoring — product engineers, QA leads — had no interest in learning HCL. They knew the URLs, the workflows, the failure cases. We were asking them to learn an infrastructure tool to do a product task.

We switched to CSV as the config layer. One row per monitor:

name,url,type,frequency_min,tags
checkout-flow,https://example.com/checkout,BROWSER,5,payments,critical
api-health,https://api.example.com/health,SIMPLE,1,api

The Terraform modules stayed. Engineers just never see them. Within weeks, QA engineers and product managers were submitting PRs to add monitoring for features they were shipping. That had never happened before.

The right abstraction lowers the contribution threshold more than any documentation.

Validate Early

The original pipeline: CSV → Terraform plan → cryptic error three minutes later. Terraform errors for malformed fields are not friendly to someone who has never used Terraform.

One validation step at the top of the pipeline, before Terraform runs, changed this. Wrong value? You get this:

Error: 'frequency' must be one of: 1, 5, 10, 15, 30, 60. Got: 45

Seconds, not minutes. Non-engineers can act on it.

Push validation as early as possible. Make errors as specific as possible.

Local Emulation Is Not a Nice-to-Have

Scripted monitors are JavaScript that runs inside New Relic’s container runtime. Without local emulation the feedback loop was: write script → commit → push → wait for pipeline → check New Relic. Minutes per iteration.

New Relic publishes the same runtime as a Docker image. Running it locally collapsed the loop to seconds. We added this after months of painful debugging cycles. It should have been day one.

Build local dev tooling early. The cost is days. The payback is every engineer who touches the project after you.

Remote State From Day One

We started with local Terraform state. Only one person could safely run terraform apply at a time. State conflicts happened when two engineers worked at once and recovery was manual.

Migrating to remote state with locking was straightforward — but it created risk during the migration. It should have been the starting point.

For any IaC project with more than one contributor, remote state with locking is a prerequisite, not an optimisation.

Rate Limits Surface at Scale

Past 200 monitors, applies started hitting New Relic API rate limits. The fix:

terraform apply -parallelism=3

The default is 10. That is fine for small stacks. It is not fine when you are updating dozens of resources at once.

Test at scale before you need to. A 300-resource apply behaves very differently from a 50-resource one.

The Audit Trail Is the Product

Semantic versioning with changelogs started as engineering hygiene. It became the feature that built trust with compliance and security teams. Every change had a version, a changelog entry, and a linked ticket. They could see the full history of what was monitored, what changed, and why.

Treat the audit trail as a deliverable, not a side effect.

The engineering was the easy part. The hard part was building something people actually use. That means the right abstraction, fast feedback, and a deployment process reliable enough that contributing does not feel risky.
