Lessons from Rebuilding a PHP Monolith into a Modern Stack

What actually breaks when you migrate a 6-year-old e-commerce platform — the technical surprises, the unexpected wins, and what I'd do differently.

Related project: E-Commerce Platform

A 6-year-old PHP monolith. Every business rule buried in code, no documentation, one engineer who remembered why half of it worked. We rebuilt it on React + Node.js. Here is what actually happened.

Data Consistency Is the Hard Part

The technology switch was not the hard part. The data was.

Six years of organic growth left the database full of rules that lived only in PHP code. We spent three weeks mapping every place inventory could change. Eleven different code paths could decrement stock — each with slightly different logic for backorders and reservations.

Before writing a single line of new code, we ran both systems in parallel and logged every divergence:

result_old = legacy.decrement_stock(item_id, qty)
result_new = new_service.decrement_stock(item_id, qty)
if result_old != result_new:
    log.warning("divergence", item=item_id, old=result_old, new=result_new)

Two weeks of shadow mode. Fourteen edge cases caught before launch.

Why Caching Actually Helped Here

Every slow site gets the same advice: add caching. Usually applied without thinking about what to cache.

The access pattern here was genuinely cache-friendly:

  • Product catalogue changes a few times per day
  • 80%+ of traffic is browse and search, not checkout
  • Session data is small and user-specific

A 5-minute TTL on catalogue data removed most database load during browse. Checkout bypassed cache entirely and hit the database with row-level locks — inventory freshness is critical there.

Cache the read-heavy paths. Never the write-critical ones.

Stripe Was Easier Than Expected

We expected pain. The Checkout Sessions API meant we never touch card data — create a session, redirect the user, handle the webhook on return.

The only tricky part was idempotency. Webhooks retry on network failure. The fulfillment handler had to be safe to call twice:

INSERT INTO processed_events (event_id) VALUES ($1)
ON CONFLICT (event_id) DO NOTHING
RETURNING event_id;
-- No row returned = already processed, skip fulfillment

Same transaction as the order update. Atomic. Safe to retry.

What I Would Do Differently

Ship the CI/CD pipeline on day one. We added GitHub Actions in week 3. The manual deploy process was slowing everyone down and causing late-night anxiety before each release. Start with automation.

Do not migrate the schema at the same time as the application. We tried to modernise the schema during the migration. This doubled the risk. Keep the schema stable, ship the new app against the old schema, then evolve the schema separately once the app is proven.

Write load tests before you think you need them. We found the pg-pool connection limit issue on the first staging load test, not in production. That was lucky — because we ran k6 before launch. Luck is not a plan.
