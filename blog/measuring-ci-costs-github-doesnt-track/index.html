Measuring the CI Costs GitHub Doesn't Track

GitHub's billing API tells you nothing about self-hosted runner usage — it's your compute, so GitHub doesn't see it. Here's how we built visibility from scratch using the Jobs API.

Related project: Self-Hosted GitHub Actions Runner Fleet

We moved from GitHub-hosted to self-hosted runners and saved money. We knew we saved money. We just could not prove it or show how much.

GitHub’s billing API only tracks managed runner minutes. Self-hosted runners run on your EC2 — GitHub never sees that time, so it never appears in any dashboard. This is how we built the measurement pipeline from scratch.

The Data GitHub Does Expose

GitHub does not track self-hosted runner minutes. But it does track job execution. Every job has a start timestamp and a completion timestamp in the Jobs API.

That is enough. The approach:

  1. Find which workflows use self-hosted runners
  2. Fetch all runs within the billing cycle
  3. Sum job durations from timestamps
  4. Aggregate by workflow and repository

No special permissions needed — a standard org-scoped token covers all of this.

Finding Self-Hosted Workflows

Iterating every repo and fetching every workflow file to find runs-on: [self-hosted, ...] would be slow and expensive in API calls.

The code search API solves this:

query = 'org:your-org "runs-on: [self-hosted" language:yaml'
results = github.search_code(query)

This returns every workflow file in the org that contains the self-hosted declaration — without touching anything else. From the results you get the repo name and workflow path, enough to resolve workflow IDs and start fetching run data.

Computing Duration

For each workflow, fetch runs in the current billing cycle and sum job-level timing:

for run in workflow.get_runs(created=f">={cycle_start}"):
    for job in run.jobs():
        if job.started_at and job.completed_at:
            duration_seconds = (job.completed_at - job.started_at).total_seconds()
            duration_minutes = math.ceil(duration_seconds / 60)

math.ceil matters. GitHub rounds every job up to the nearest minute for managed runner billing. We apply the same logic to self-hosted durations so the numbers are directly comparable.

Billing Cycle Boundaries

GitHub’s billing cycle resets on the 25th of each month — not the calendar month boundary. Report against a calendar month and you overcount or undercount depending on when you run it.

today = date.today()
if today.day >= 25:
    cycle_start = today.replace(day=25)
else:
    first_of_month = today.replace(day=1)
    cycle_start = (first_of_month - timedelta(days=1)).replace(day=25)

This looks obvious once written. It is not obvious when your report is off by a week and you are trying to figure out why.

OS Multipliers on Managed Runners

GitHub’s billing API returns raw minutes but does not apply the OS multipliers that determine actual cost:

MULTIPLIERS = {"UBUNTU": 1, "WINDOWS": 2, "MACOS": 10}

normalised = sum(
    minutes * MULTIPLIERS[os]
    for os, minutes in billing.items()
)

Normalising to equivalent Ubuntu minutes lets you compare managed and self-hosted on the same scale. In our case, a handful of Windows workflows were responsible for a disproportionate share of the bill — invisible without this step.

Staying Under Rate Limits

Cache workflow discovery. Workflow files change slowly. Cache the discovered list across a reporting run — avoid re-searching on every iteration.

Filter server-side. The created parameter on the runs API filters by date on GitHub’s side. You are not fetching thousands of runs to discard most of them.

Use conditional requests. For repos with no recent runs, send If-None-Match with the previous response ETag. A 304 response does not count against your rate limit.

When a platform does not expose the measurement you need, the raw data to build it yourself is usually there — just not pre-aggregated. GitHub exposes job timestamps. From timestamps, you can derive everything a billing endpoint would give you.
