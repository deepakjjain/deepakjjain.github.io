API Design Principles I Keep Coming Back To

Not a comprehensive REST tutorial — just the handful of decisions that repeatedly make the difference between an API that's a joy to consume and one that causes 11pm Slack messages.

A good API and a bad API can look almost identical on the surface. The difference is usually a few small decisions made early that nobody revisited. Here are the ones that consistently matter.

Make Errors More Useful Than Successes

When a call succeeds, the response shape matters less — you got what you wanted. When it fails, the error is everything.

Bad:

{ "error": "Bad request" }

Good:

{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Request validation failed",
    "details": [
      { "field": "email", "message": "Must be a valid email address" },
      { "field": "role", "message": "Must be one of: admin, editor, viewer" }
    ],
    "requestId": "req_abc123"
  }
}

The requestId is underrated. When a consumer files a bug report, it finds the exact log entry in seconds instead of guessing from a timestamp.

Cursor Pagination, Not Page Numbers

Page-number pagination (?page=3&limit=20) breaks when data changes between requests. A row inserted mid-pagination gives you a duplicate on the next page.

Cursor pagination (?after=cursor_xyz&limit=20) returns a stable token based on the last item’s position. No duplicates. No skipped rows.

The trade-off: you cannot jump to page 50. For infinite scroll and streaming lists — most real use cases — this does not matter.

Version From Day One

Even if you are the only consumer. Even if the API feels stable.

/api/v1/users costs nothing now and prevents the “we need to change the response shape but cannot break the mobile app” conversation later.

Use path prefixes, not headers. Path versions are visible in logs, browser devtools, and curl. Header versioning is clean in theory and painful to debug in practice.

Separate 404 from 403

Returning 404 when a resource exists but the caller has no access leaks information. Returning 403 for everything makes permission errors indistinguishable from typos.

The rule:

  • 404 — the resource does not exist for anyone
  • 403 — the resource exists, but you are not allowed to see it
  • 401 — you are not authenticated at all

Semantically correct. Gives consumers enough context to show the right UI state without revealing data they should not know about.

Design for the Consumer, Not the Database

The most common anti-pattern: API responses that mirror the database schema. Separate tables become separate endpoints. Join tables leak into responses. Internal IDs appear everywhere.

The consumer does not care that users and profiles are separate tables. They want a single GET /users/:id that has everything needed to render a profile page.

Design the response around what the consumer needs to do. Then figure out how to assemble it on the server.
