How Operational Transformation Actually Works (and When to Use It)

A practical breakdown of OT for collaborative editing — the algorithm, the tradeoffs, and why we chose it over CRDTs for DevCollab.

Related project: DevCollab

Two users open the same document. Both see "Hello". One inserts " World" at position 5. The other deletes "H" at position 0. Depending on which edit arrives first, you get a different result — or a crash.

This is the core problem of collaborative editing. Here is how Operational Transformation (OT) solves it, and why we picked it over CRDTs.

The Problem in Concrete Terms

  • Alice inserts " World" at position 5 → "Hello World"
  • Bob deletes "H" at position 0 → "ello"

Server receives [Alice, Bob]: applies Alice first → "Hello World", then deletes position 0 → "ello World". Fine.

Server receives [Bob, Alice]: applies Bob first → "ello", then inserts at position 5. "ello" is 4 characters. Crash.

OT solves this by adjusting the position of one operation based on the other — so the intent is preserved regardless of arrival order.

The Transform Function

Every text change is either insert(pos, text) or delete(pos, length). The transform function adjusts positions:

transform(insert(5, " World"), delete(0, 1))
  → insert(4, " World")  // one char deleted before position 5, so shift left by 1

The key property: both orderings of the same two operations must produce the same final document. That is called convergence.

We verified this with a property-based test suite — thousands of randomly generated concurrent operation pairs. It found two bugs that manual testing would never have surfaced.

Why Not CRDTs?

CRDTs (Conflict-free Replicated Data Types) are cleaner in theory — no central server needed, peer-to-peer friendly. For a document editor you would use a sequence CRDT like RGA or LSEQ.

The cost: CRDTs attach metadata to every character to track ordering. For documents that get edited heavily, that metadata grows with the edit history. For our use case — engineering teams with dense editing patterns — the memory overhead was meaningful.

OT with a central server is simpler to reason about. The server is the source of truth. DevCollab already had a server for auth, presence, and storage — OT was the straightforward choice.

What ot-json0 Gave Us

We used ot-json0 instead of writing transform functions from scratch. It handles insert, delete, and move operations on JSON tree structures — not just flat text strings.

The part we built ourselves: the revision protocol. Clients tag each operation with the server revision it was based on. The server transforms the operation against every operation that arrived since that revision, then broadcasts the result to other clients.

Three Lessons

Test convergence exhaustively. Random input testing finds bugs that manual testing cannot. Do not skip this.

Keep presence separate from content. Cursor positions and user indicators are ephemeral state. They go through Socket.io directly — not the OT pipeline. Mixing presence into the document model adds complexity with no benefit.

Version vectors are worth the complexity. Tracking per-client revision vectors instead of a single global counter means a reconnecting client only catches up on what it missed — not the full document history.
